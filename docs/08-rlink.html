9  Linking people with rLink()

Chapter 6 introduces rLink() alongside the rest of the linkage toolbox. This chapter is about rLink() itself, worked from the simplest call that does anything useful up to a staged production linkage, on the one problem the function was written for: deciding which records are the same person.

Person linkage has a shape of its own. The fields are a name — split into first, middle and last in one system and not split at all in the next — a date of birth, an address, a postcode, a phone number, an email address and a sex or gender code. Each of them fails in its own way, and the whole craft of the thing is knowing which failure you are looking at:

Field How it goes wrong What that means for the link
Surname Marriage, hyphenation, lost apostrophes, transliteration, typing Common, and not random: a disagreement is weak evidence against
Given name Nicknames, initials, order swapped with the middle name Same; ROBERT/BOB is not a typing error
Middle name Simply not collected, or collapsed into the given-name field Missing far more often than wrong
Date of birth Day/month transposed, a year out, 1 January placeholders Strong evidence, but the placeholders will ruin a block
Address People move. Abbreviations, unit prefixes, free-text additions Agreement is strong; disagreement says almost nothing
Postcode Leading zeros lost to a numeric column A cheap, high-value blocking key once it is zero-padded
Phone Shared by a household, re-used, reformatted, stale Agreement is very strong, disagreement very weak
Email Keeps a maiden name for years; case and whitespace The same: agreement is near-proof, absence is routine
Sex / gender M/F/U against Male/Female/Unknown/blank Nearly free, and useful mostly as a filter

The recurring lesson is in the last column. For a near-identifier — phone, email, address — agreement and disagreement are not mirror images, and a missing value is a third thing again, not a disagreement. Most of the advanced material below is about building comparisons that respect that.

9.1 The smallest useful call

Two tiny files: five people in one, and four of the same five, recorded differently, in the other.

hospital <- data.frame(
    frame_id   = c("HOS-01", "HOS-02", "HOS-03", "HOS-04", "HOS-05"),
    first_name = c("MARGARET", "ROBERT", "THI MINH", "WILLIAM", "ELENI"),
    last_name  = c("O'BRIEN", "SMITH", "NGUYEN", "WILLIAMS", "PAPADOPOULOS"),
    dob        = as.Date(c("1948-11-02", "1979-07-23", "1962-03-14",
                           "1990-06-08", "1955-01-30")),
    postcode   = c("3121", "4000", "4032", "3065", "3181")
)

Four things happened that are worth naming, because everything later in this chapter is a variation on them.

block_1 is where to look. Comparing every record with every other record is quadratic and almost all of it is wasted. Blocking on dob says: only ever compare two people born on the same day. That is four comparisons here instead of twenty.

compare is what to measure. Each element is a comparator call whose first argument is the column to compare. The score column is named after the list element — last, first — and an unnamed element falls back to <column>_<comparator>.

Both are ordinary R expressions evaluated against the data. Nothing was prepared beforehand. soundex(last_name) or fsubstr(postcode, 1, 2) would have worked exactly as well as a bare column name, in either argument.

1 always means an exact match. jaro_winkler() already returns 1 for identical strings, but levenshtein() returns 0 and the RapidFuzz fuzz_*() scorers return 100. rLink() probes each comparator and converts, so you never have to remember which way a metric runs:

rLink(hospital, registry, block_1 = list(dob),
      compare = list(lev = levenshtein(last_name)))$lev
[1] 0.8571429 1.0000000 1.0000000 0.8750000

What it decided is recorded on the result, and is worth reading once per project:

attr(pairs, "compare")

2 first jaro_winkler first_name first_name similarity    higher        4

9.2 Blocking, properly

Blocking decides what the run costs and what it is able to find. A true pair that no pass puts in the same block can never be recovered, no matter how good the comparators are. It is where a linkage usually goes wrong, so rLink() makes it inspectable.

Check the blocking before you run it

dry_run = TRUE builds every key, checks every argument, and stops without generating a single pair. On real files this takes about as long as reading them, which means a blocking design can be argued about before anyone waits an hour for it.

Several passes, and why

A pair is a candidate if it agrees on the key of any one pass. Each pair is reported once, and pass records the first pass that found it. Inside a pass, list() joins terms into one key, so list(soundex(surname), dob) requires the same surname code and the same date of birth.

That structure is how you cover the error modes one at a time. The design above reads:

  • surname_dob — the workhorse. Survives spelling, not a wrong date.
  • surname_year — survives a transposed day and month, which the first pass cannot. This is the expensive one.
  • given_dob — survives a married surname, where the registered name is gone entirely and no amount of string comparison will find it.
  • name_postcode — survives a wrong date of birth, as long as they have not moved.

No single key could do any two of those. That is what multiple passes are for, and the whole art is adding the pass that covers an error you can show exists, not the pass that feels thorough.

Because these files come with a known truth, each pass can be audited:

cand <- rLink(
    enrol, claims_std,
    block_1 = list(
        surname_dob   = list(soundex(surname), dob),
        surname_year  = list(soundex(surname), format_date(dob, "y")),
        given_dob     = list(soundex(given_name), dob),
        name_postcode = list(soundex(surname), fsubstr(given_name, 1, 1),
                             postcode)
    ),
    compare = list(
        surname  = jaro_winkler(surname),
        given    = jaro_winkler_tokens(given_name),
        dob      = date_compare(dob),
        address  = jaro_winkler_tokens(street_address),
        postcode = (function(a, b) as.numeric(a == b))(postcode)
    ),
    pair_id = c("enrol_id", "claim_id"),
    keep = c("given_name", "surname", "dob", "sex", "street_address",
             "postcode", "phone", "email")
)

Read that table as a cost sheet. surname_dob is almost pure signal: it finds nearly every match at a yield around 0.99. surname_year is the opposite — roughly two thirds of all the candidates, at a yield of about 0.03 — because dropping the day and month from the key makes the blocks fifty times bigger. It is still worth having: it is the only pass that survives a transposed date of birth, and the few hundred pairs it alone contributes are exactly the ones the other three cannot reach. But it is the first pass to tighten if the run gets too big, and the one to point at when someone asks where the time went.

Missing keys never pair

A record whose key is missing pairs with nothing. That is what makes it safe to block on an incomplete field: the records with no date of birth simply do not appear in the passes that use it, rather than colliding into one enormous block of NA.

With the default match_missing = FALSE, a missing value in any term makes the whole key for that pass missing. na_strings lists the text that counts as missing — "" by default, which is what makes the blank phone numbers in the claims file behave like absences rather than like a value everybody shares.

a <- data.frame(surname = c("SMITH", NA, "JONES"))
b <- data.frame(surname = c("SMITH", NA))
c(default = nrow(rLink(a, b, block_1 = list(surname))),
  match_missing = nrow(rLink(a, b, block_1 = list(surname),
                             match_missing = TRUE)))
      default match_missing 
            1             2

match_missing = TRUE treats “missing” as a value in its own right. It is occasionally what you want, and almost never what you want on a near-identifier: two people with no recorded phone number have nothing in common.

block_2, when the files disagree about shape

block_2 gives the second file its own expressions, pass for pass, for when the same information is stored differently:

raw <- claims
raw$dob_text <- raw$date_of_birth               # "DD/MM/YYYY"
raw$surname_raw <- ftrimws(fsplit_field(fsquish(fupper(raw$patient_name)),
                                        ",", 1))

head(rLink(enrol, raw,
           block_1 = list(list(soundex(surname), format(dob, "%d/%m/%Y"))),
           block_2 = list(list(soundex(surname_raw), dob_text)),
           compare = list(sn = jaro_winkler(surname | surname_raw)),
           keep    = c("surname", "surname_raw"))[, -1], 3)
   index_1 index_2  pass       block_key surname_1 surname_raw_2    sn
     <int>   <int> <int>          <char>    <char>        <char> <num>
1:       3    2946     1 W452|25/12/1965  WILLIAMS      WILLIAMS     1
2:       4    1570     1 S530|28/11/1952     SMITH         SMITH     1

surname | surname_raw is the same idea in compare: the left of the | is evaluated against data_1, the right against data_2. Either side can be any expression, so soundex(family_name) | surname_code works too. Such an element has no single column to name itself after, so it must be given a name.

The sorted neighbourhood, for keys that differ at the end

An exact key cannot put SMITH and SMITHE together. block_method = "sorted_neighbourhood" sorts the distinct keys and pairs records within (window - 1) / 2 places of each other as well as those with equal keys. Methods are set per pass, so a strict pass and a forgiving one run in the same call:

mixed <- rLink(
    enrol, claims_std,
    block_1      = list(strict = list(soundex(surname), dob),
                        near   = surname),
    block_method = c("exact", "sorted_neighbourhood"),
    window       = 3,
    compare      = list(sn = jaro_winkler(surname)),
    keep         = character()
)
attr(mixed, "blocking")$passes[, c("label", "method", "n_expected", "n_pairs")]
   label               method n_expected n_pairs
1 strict                exact       9797    9797
2   near sorted_neighbourhood    1573807 1564239

The window also pairs unrelated alphabetical neighbours, by design. It belongs in a pass whose candidates are then scored, never on its own.

9.3 Comparing person fields

Any function of two character vectors is a comparator, so the choice of metric is a one-word edit. What matters is matching the metric to the way the field fails.

Names

A surname is a short string with substitutions and omissions: jaro_winkler() is the standard, and editex() costs phonetic substitutions (PH/F, C/K) less. A given-name field that may hold a middle name, an initial, or the words in another order is a token problem, not an edit-distance one:

a <- c("JOHN PAUL", "MARY JANE", "ROBERT", "LI WEI")
b <- c("PAUL JOHN", "MARY J", "BOB", "WEI LI")
data.frame(a, b,
           jaro_winkler = round(jaro_winkler(a, b), 3),
           tokens       = round(jaro_winkler_tokens(a, b), 3),
           monge_elkan  = round(monge_elkan(a, b), 3))
          a         b jaro_winkler tokens monge_elkan
1 JOHN PAUL PAUL JOHN        0.407  1.000       1.000
2 MARY JANE    MARY J        0.933  0.925       0.887
3    ROBERT       BOB        0.500  0.500       0.500
4    LI WEI    WEI LI        0.667  1.000       1.000

The token comparators win decisively where the words moved (JOHN PAUL/PAUL JOHN, LI WEI/WEI LI), which is the failure plain Jaro-Winkler cannot see at all — 0.407 for two identical names in the other order. Where a word is merely abbreviated (MARY JANE/MARY J) plain Jaro-Winkler does fine, and the tokens buy nothing. Pick the comparator for the error you have.

No string metric recovers ROBERT/BOB: all three score it 0.5, and they are right to — the strings really are that different. Nicknames are a lookup problem, and freplace_tokens() against a nickname table before linking is worth more than any comparator choice.

First / middle / last against given / last. Two systems often split names differently, and the usual mistake is to compare the fields that happen to share a name. Compare the information instead: build one comparable field on each side with |.

# enrol has given / middle / surname; this extract has only given / surname,
# with the middle name folded into the given-name field where it was known.
folded <- claims_std

Dates of birth

A string comparator is handed text whatever the column holds, which is what makes jaro_winkler(dob) work on a Date at all. But a date is not a string: 1 January and 2 January are one day apart, not two characters apart. date_compare() is handed the column as it is stored:

A transposed day and month is a different error again, and it is worth its own flag rather than a tolerance — 14/03 against 03/14 is six months apart, which no distance will forgive:

transposed <- function(a, b) {
    pa <- date_parts(a); pb <- date_parts(b)
    as.numeric(pa$year == pb$year & pa$day == pb$month &
               pa$month == pb$day & pa$day != pa$month)
}
swapped <- rLink(enrol, claims_std,
                 block_1 = list(list(soundex(surname), format_date(dob, "y"))),
                 compare = list(dob  = date_compare(dob),
                                swap = transposed(I(dob)),
                                sn   = jaro_winkler(surname)),
                 keep = character())

I() is what asks for the column as it is stored rather than as text. numeric_compare() and date_compare() do it for you; a comparator of your own asks for it explicitly.

Near-identifiers: phone, email, address

Here is the point this chapter keeps returning to. For a phone number, agreement is near-proof and disagreement is almost no evidence at all, because people change numbers and households share them. Scoring one with jaro_winkler() is actively harmful: it produces a confident-looking 0.6 for two completely different numbers.

Build the comparison to say the three things that can actually be true — agrees, disagrees, not known — and let the missing value stay missing:

# Compare digits only, so "0412 345 678", "0412345678" and "+61 412 345 678"
# are the same number; NA where either side is blank, which is not the same
# fact as a disagreement.
same_phone <- function(a, b) {
    da <- fgsub("[^0-9]", "", a); db <- fgsub("[^0-9]", "", b)
    da <- fgsub("^61", "0", da);  db <- fgsub("^61", "0", db)
    out <- as.numeric(da == db)
    out[!nzchar(da) | !nzchar(db) | is.na(da) | is.na(db)] <- NA_real_
    out
}
same_email <- function(a, b) {
    la <- flower(ftrimws(a)); lb <- flower(ftrimws(b))
    out <- as.numeric(la == lb)
    out[!nzchar(la) | !nzchar(lb) | is.na(la) | is.na(lb)] <- NA_real_
    out
}

contact <- rLink(
    enrol, claims_std,
    block_1 = list(list(soundex(surname), format_date(dob, "y"))),
    compare = list(sn    = jaro_winkler(surname),
                   phone = same_phone(phone),
                   email = same_email(email)),
    keep = character()
)
sapply(contact[, c("phone", "email")],

A pair whose phone numbers agree is a match essentially always, and one whose emails agree very nearly so — against a base rate of about a third. That is an enormous amount of evidence from a field most people never think to compare, and it costs one exact test.

Be careful reading the other direction, though. Disagreement looks informative here (7.5% against a 32% base rate) partly because this simulator only reassigns a number for one matched person in eight. Real contact data goes stale faster, and real households share landlines, so on a live file the gap between disagrees and not known is narrower than this. The safe design is the one above either way: score agreement, and let non-agreement be NA rather than a confident zero.

An address behaves the same way, with the extra wrinkle that it is multi-word and abbreviated, so it wants a token comparator rather than an exact test. Sex is the cheapest field of all, and it is most useful not as a score but as a condition — see filter, below.

9.4 Filtering while scoring

Blocking is deliberately generous, so most candidates are not matches and get thrown away the moment they are scored. filter does the throwing away inside rLink():

kept <- rLink(
    enrol, claims_std,
    block_1 = list(list(soundex(surname), format_date(dob, "y"))),
    compare = list(sn = jaro_winkler(surname),
                   gn = jaro_winkler_tokens(given_name)),
    filter  = sn >= 0.85 & gn >= 0.80 & (sex_1 == sex_2 | sex_1 == "U" | sex_2 == "U"),
    pair_id = c("enrol_id", "claim_id"),
    keep    = c("surname", "given_name", "sex")
)
unlist(attr(kept, "filter")[c("n_candidates", "n_scored", "n_kept")])
n_candidates     n_scored       n_kept 
       32048        32048        10327

The rule is an ordinary R expression giving TRUE for the pairs to keep. It can name any score, pass, and any column of either input under its suffix. Three properties make it more than a convenience:

Conditions that read no score are applied first. The sex clause above needs no comparator, so it runs before scoring and the comparators never see the pairs it drops. The order you write the conditions in makes no difference; the result is identical to scoring everything and subsetting.

The expensive columns are built only for survivors. pair_id above all — R takes about a second to make a million new strings, whoever asks it to — and then the carried columns.

The 2^31 candidate-pair ceiling goes away. Pairs are generated, scored and thinned a slice at a time, so the full candidate set never exists at once; only the pairs kept have to fit in one table.

A rule that mentions no score needs no compare at all, which makes filter a way to express a candidate condition that no blocking key could:

nrow(rLink(enrol, claims_std,
           block_1 = list(list(soundex(surname), fsubstr(given_name, 1, 1))),
           filter  = abs(as.numeric(dob_1 - dob_2)) <= 31,
           keep    = character()))

9.5 Identifying pairs, so a judgement survives

pair_id identifies each pair. By default it is "<id_1>|<id_2>" built from the frame_id column of each input, and it falls back to numbering the pairs when either input has no such column. Two different names are given as pair_id = c("enrol_id", "claim_id").

This matters more than it looks. An identifier built from the records is stable: the same two records give the same pair_id whatever blocking found them. A row number is not.

run_a <- rLink(enrol, claims_std,
               block_1 = list(list(soundex(surname), dob)),
               compare = list(sn = jaro_winkler(surname)),
               pair_id = c("enrol_id", "claim_id"), keep = character())
run_b <- rLink(enrol, claims_std,
               block_1 = list(list(soundex(given_name), dob)),
               compare = list(sn = jaro_winkler(surname)),
               pair_id = c("enrol_id", "claim_id"), keep = character())
c(run_a = nrow(run_a), run_b = nrow(run_b),
  same_pairs = length(intersect(run_a$pair_id, run_b$pair_id)))
     run_a      run_b same_pairs

Every clerical judgement recorded in Chapter 10 is filed against this column, which is the only reason those judgements still apply after the blocking is changed and the linkage re-run. An identifier containing "|" is an error rather than an ambiguous key, and missing or repeated identifiers raise a warning saying how many.

Building it is the slowest thing rLink() does on a large result. filter avoids it for the pairs it drops; pair_id = NULL avoids it altogether, for a run whose pairs will be thresholded and clustered but never reviewed. attr(x, "timings") reports it as its own stage:

9.7 Staged linkage

A large linkage is rarely one run. The usual shape is a strict pass whose links nobody needs to look at, then a looser pass over what is left, and two arguments keep the second from repeating the first.

exclude names pairs to leave out. They are dropped as soon as they are found, before scoring, so pairs already settled cost nothing the second time. Given as a character vector they are read as pair_ids and found again through the identifier columns — which is what makes them safe to carry between runs, since the files may have been re-ordered, added to or cut down in between.

rLink_unmatched() is the other half: the records that no accepted link reaches, which are the ones a second run is for.

# Stage 1: strict. Same surname code and full date of birth, names close.
stage1 <- rLink(
    enrol, claims_std,
    block_1 = list(list(soundex(surname), dob)),
    compare = list(sn = jaro_winkler(surname),
                   gn = jaro_winkler_tokens(given_name)),
    filter  = sn >= 0.95 & gn >= 0.90,
    pair_id = c("enrol_id", "claim_id"), keep = character()
)

# Stage 2: looser, over the records stage 1 did not reach, and explicitly
# not re-examining anything stage 1 already settled.
left_1 <- rLink_unmatched(stage1, side = 1, n = nrow(enrol))
left_2 <- rLink_unmatched(stage1, side = 2, n = nrow(claims_std))

stage2 <- rLink(
    enrol[left_1, ], claims_std[left_2, ],
    block_1 = list(list(soundex(given_name), dob),
                   list(soundex(surname), postcode)),
    compare = list(sn = jaro_winkler(surname),
                   gn = jaro_winkler_tokens(given_name),
                   ad = jaro_winkler_tokens(street_address)),
    filter  = sn >= 0.80 | ad >= 0.90,
    pair_id = c("enrol_id", "claim_id"), keep = character()
)

Stage 1 is perfectly precise on this data, and that is the point: those links never need a human. Stage 2 is where the judgement is, and Chapter 10 is about making that judgement recordable.

One trap in that code. Stage 2 was run on subsets, so its index_1 and index_2 are positions in enrol[left_1, ] and claims_std[left_2, ], not in the original files — left_1[index_1] converts them back. This is precisely why a stable pair_id is worth having: it means the same thing in both stages, so the two results stack without any index arithmetic at all.

The same two arguments also express “re-run with better blocking, but do not ask me about the pairs I have already ruled on”:

               compare = list(sn = jaro_winkler(surname)),
               pair_id = c("enrol_id", "claim_id"),

12  A worked record-linkage pipeline

This chapter links two files of people end to end: a service enrolment extract and a claims extract from a different system, holding many of the same people. Nothing is pre-cleaned. Every step is one of the functions in this package, and because the data carry a hidden person_id, every claim made along the way is measured rather than asserted.

The shape of the problem is always the same:

Step Question Section
1 What is actually in these columns? sec-wf-profile
2 Do the two files agree on types and spelling? sec-wf-standardise
3 Which records are even worth comparing? sec-wf-block
4 How alike is each candidate pair, field by field? sec-wf-score
5 Which pairs do we accept, and which go to a human? sec-wf-decide
6 What is one person’s identifier across both files? sec-wf-entities
7 How well did it work, and what did it cost? sec-wf-evaluate

12.2 Step 1: profile before you match

The fastest way to be wrong about a column is to assume you know its shape. string_shape() collapses each value to a character-class pattern, so the distinct formats in a column are a table() away:

head(sort(table(string_shape(claims$date_of_birth)), decreasing = TRUE), 3)
99/99/9999 
     37500 
head(sort(table(string_shape(claims$patient_name)), decreasing = TRUE), 5)

  Aaaaaa, Aaaa   Aaaaa, Aaaaa  Aaaaaa, Aaaaa    Aaaaa, Aaaa Aaaaaa, Aaaaaa 
           351            344            332            293            263

Every date of birth is 99/99/9999, so one fixed format will parse the column. The name column has many shapes, which is the signal that it needs parsing rather than comparing as it stands.

Two more questions worth asking of every incoming column — how much is missing, and how much is a placeholder:

c(gender_blank   = mean(!nzchar(claims$gender)),
  gender_unknown = mean(claims$gender == "Unknown"),
  name_untrimmed = mean(claims$patient_name != trimws(claims$patient_name)),
  dob_jan_1      = mean(fgrepl("^01/01/", claims$date_of_birth)),
  postcode_short = mean(fnchar(as.character(claims$postcode)) < 4))
  gender_blank gender_unknown name_untrimmed      dob_jan_1 postcode_short 
    0.06288000     0.06189333     0.25005333     0.02240000     0.32978667

About one date of birth in forty-five is 1 January — far more than the 1-in-365 a real population gives. That is the placeholder a clerk types when the date is unknown, and a blocking pass on the exact date would build one huge useless block out of it. sec-wf-block caps it, and a real project would set those dates to NA instead.

12.3 Step 2: standardise, field by field

The goal is one data frame per file with the same column names, the same types and the same spelling conventions. Every line below is vectorised over the whole column.

The name field

fupper() and fsquish() first, so nothing downstream has to think about case or whitespace again; then fsplit_field() on the comma; then freplace_tokens() to drop the titles. freplace_tokens() matches whole tokens from a dictionary in one pass, so "DR" goes and "DRUMMOND" stays — which a gsub("DR", "", ...) would not manage.

titles <- c("MR", "MRS", "MS", "MISS", "DR", "PROF", "REV", "SIR")

name  <- fsquish(fupper(claims$patient_name))
surn  <- ftrimws(fsplit_field(name, ",", 1))
rest  <- fsquish(freplace_tokens(ftrimws(fsplit_field(name, ",", 2)),
                                 titles, rep("", length(titles))))
given  <- fsplit_field(rest, " ", 1)
middle <- fsplit_field(rest, " ", 2)

data.frame(claims$patient_name, surn, given, middle)[1:6, ]

2       Sheni, Fena Ryan    SHENI   FENA   RYAN
3   Campbell,  Mr Pell   CAMPBELL   PELL   <NA>
4     Gofy, Andrew Keski     GOFY ANDREW  KESKI
5         Fises, Dr Loll    FISES   LOLL   <NA>

Apostrophes and hyphens are the other recurring name problem: the same person is O'BRIEN in one file and OBRIEN in the other, SMITH-JONES here and SMITH JONES there. Rather than choose, keep the name as given and compare on a form that ignores the difference. Three functions do different parts of that job:

              "MULLER", "MÜLLER", "SMITH-JONES", "SMITH JONES")

ascii_fold() is the one that matters for MÜLLER: it folds accented Latin letters to ASCII, so a file that lost its accents still matches one that kept them. fingerprint() (OpenRefine’s clustering key) lower-cases, folds, strips punctuation and sorts the words, which is what makes SMITH-JONES and SMITH JONES meet — but note that it keeps O BRIEN apart from OBRIEN, because there the space creates a second word rather than joining two. Stripping to letters alone collapses all four of the O'BRIEN spellings, at the cost of also collapsing names that differ only in their spacing. A blocking key wants the aggressive form; a score wants the gentle one, which is why jaro_winkler_tokens() exists — it folds punctuation and spacing inside the comparison, so the raw names can be compared as they were recorded:

jaro_winkler_tokens(c("O'BRIEN", "SMITH-JONES", "O'BRIEN"),
                    c("O BRIEN", "SMITH JONES", "OBRIEN"))
[1] 1 1 1
jaro_winkler(c("O'BRIEN", "SMITH-JONES", "O'BRIEN"),
             c("O BRIEN", "SMITH JONES", "OBRIEN"))
[1] 0.9142857 0.9636364 0.9571429

The date of birth

fas.Date() parses one fixed layout with no locale, no strptime() and no format guessing, and validates the calendar, so an impossible date becomes NA instead of silently rolling over:

dob <- fas.Date(claims$date_of_birth, format = "dmy")
c(parsed = sum(!is.na(dob)), failed = sum(is.na(dob)))
parsed failed 
 37500      0 
# Strictness is the point: base R's as.Date() guesses, fas.Date() refuses.
fas.Date(c("29/02/2024", "29/02/2023", "31/04/2024", "1/3/2024", NA),
         format = "dmy")
[1] "2024-02-29" NA           NA           NA           NA

2024 is a leap year and 2023 is not; 31 April does not exist; and "1/3/2024" is not "DD/MM/YYYY" — a fixed-width format means fixed-width. Any of those being NA is a finding about the data, which is what you want at this stage, rather than a wrong date to discover later.

date_parts() splits a Date into year, month and day columns in one pass, which is how the cheap partial blocking keys get built:

parts <- date_parts(dob)
head(parts, 3)

1 2012     8  28
2 1979     5   1
3 2019    11   2
head(format_date(dob, "y-m"), 3)      # "YYYY-MM", a coarser key
[1] "2012-08" "1979-05" "2019-11"

Sex, gender and the vocabulary problem

The two files use different vocabularies for the same field. Map both onto one, and keep “not recorded” distinct from “disagrees” — treating an unknown as a disagreement throws away true matches:

sex_code <- function(x) {
    x <- fupper(ftrimws(as.character(x)))
    out <- rep("U", length(x))
    out[x %in% c("M", "MALE", "1")]   <- "M"
    out[x %in% c("F", "FEMALE", "2")] <- "F"
    out
}
table(raw = claims$gender, coded = sex_code(claims$gender))
         coded
raw           F     M     U
              0     0  2358
  Female  16477     0     0
  Male        0 16344     0
  Unknown     0     0  2321

The comparison that goes with it returns agreement, disagreement, or neither:

sex_agree <- function(a, b) ifelse(a == "U" | b == "U", 0.5,
                                   as.numeric(a == b))
sex_agree(c("M", "M", "F", "U"), c("M", "F", "F", "F"))
[1] 1.0 0.0 1.0 0.5

The address

An address line is a street number, a street name, a street type and a locality, run together with the type abbreviated. Pull the unit off the front with fgsub(), split on the comma, and expand the abbreviations with a whole-token dictionary — the same freplace_tokens() trick as the titles, and the reason "ST KILDA" does not become "STREET KILDA":

street_abbrev <- c("ST", "RD", "AVE", "CT", "PL", "TCE", "PDE", "CRES",
                   "DR", "LN", "HWY", "BLVD")
street_full   <- c("STREET", "ROAD", "AVENUE", "COURT", "PLACE", "TERRACE",
                   "PARADE", "CRESCENT", "DRIVE", "LANE", "HIGHWAY",
                   "BOULEVARD")

raw_addr <- fupper(claims$address_line)
unit     <- fextract("[0-9]+", fextract("^U[0-9]+/", raw_addr))
body     <- fgsub("^U[0-9]+/", "", raw_addr)
street   <- fsquish(freplace_tokens(ftrimws(fsplit_field(body, ",", 1)),
                                    street_abbrev, street_full))
locality <- ftrimws(fgsub(" VIC$", "", fsplit_field(body, ",", 2)))

# Rows with a unit number, so the prefix is visible.
head(data.frame(claims$address_line, unit, street, locality)[!is.na(unit), ], 5)

12.4 Step 3: block, and know what each pass buys you

Comparing every enrolment record with every claim is 1,500,000,000 pairs. Blocking compares only the records that agree on some key. One key misses every true match with an error in that key, so a linkage runs several passes with keys that fail in different ways:

Pass Key Survives
1 surname code + exact date of birth any error in the given name or address
2 surname code + year of birth a transposed or shifted date of birth
3 given-name code + exact date of birth a changed or misspelled surname
4 surname code + first initial + postcode a date of birth that is wholly wrong

rLink() takes those four passes as four list()s, and the blocking keys are written as expressions, so the phonetic code and the date part are computed inside the call:

cand <- rLink(
    enrol_std, claims_std,
    block = list(
        surname_dob   = list(soundex(surname), dob),
        surname_year  = list(soundex(surname), format_date(dob, "y")),
        given_dob     = list(soundex(given_name), dob),
        name_postcode = list(soundex(surname), fsubstr(given_name, 1, 1),
                             postcode)
    ),
    # The 1 January placeholder, and the commonest surname codes, would
    # otherwise build blocks that cost more than they can return.
    max_block_size = 2000,
    keep = character()
)

Pass 1 does most of the work at a very high yield. Pass 2 is the expensive one — it is the only pass that survives a transposed day and month, and it pays for that with most of the candidates. Passes 3 and 4 add the records whose surname or date of birth is simply wrong. This table is the blocking design’s justification; a pass that adds no true pairs should be deleted, and a pass with a very low yield is the one to tighten first.

12.5 Step 4: score each candidate, field by field

A single similarity over a concatenated name hides which field disagreed. Score each field separately and keep the columns, so a reviewer can see why a pair scored what it did. rLink() puts each score next to the pair of columns it scores:

A date of birth deserves better than equal-or-not. The errors it actually carries are a transposed day and month, a year out by one, and the 1 January placeholder — so grade it, and let the weight apply to the grade:

dob_agreement <- function(a, b) {
    da <- fas.Date(a); db <- fas.Date(b)      # comparators are handed text
    pa <- date_parts(da); pb <- date_parts(db)
    ok <- !is.na(da) & !is.na(db)
    gap <- abs(as.numeric(da) - as.numeric(db))
    out <- numeric(length(a))
    # Weakest first; each line overrides the one above it.
    out[which(ok & pa$year == pb$year)]                      <- 0.3
    out[which(ok & pa$year == pb$year & pa$month == pb$month)] <- 0.5
    out[which(ok & gap <= 366)]                              <- 0.7
    out[which(ok & pa$year == pb$year &                      # day/month swap
                   pa$day == pb$month & pa$month == pb$day)]  <- 0.8
    out[which(ok & gap <= 1)]                                <- 0.9
    out[which(ok & da == db)]                                <- 1
    out[!ok] <- 0.5                           # one side missing: no evidence
    out
}
d1 <- c("1985-03-05", "1985-03-14", "1985-03-15", "1985-03-15", "1985-03-15")
d2 <- c("1985-05-03", "1985-03-15", "1986-03-15", "1985-11-02", "1985-03-15")

dob_agreement is listed as not detected in the table above, and that is the right answer: the probe is a pair of letter strings, which fas.Date() cannot parse, so nothing can be inferred from it and the scores are passed through untouched. That is harmless here because the function already returns 0–1 with 1 meaning identical. A comparator of your own that does not already run that way should either be written so it does or be left to normalise = FALSE — and the scale column is where you check which happened.

Which fields actually carry information

The weights say how much each field’s agreement is worth, and the data can be asked. For each field, compare its mean score among the pairs that are the same person with its mean among the pairs that are not — the m- and u-probabilities of the Fellegi-Sunter model, which here can be computed exactly because the truth is known:

field_info <- function(column, truth) {
    m <- mean(column[truth]); u <- mean(column[!truth])
    c(agreement_if_match = round(m, 3), agreement_if_not = round(u, 3),
      log_odds = round(log(m / u), 2))
}
truth_c <- same_person(files, scored$index_1, scored$index_2)

              middle   = scored$middle,
              sex      = scored$sex,
              address  = scored$address,
              suburb   = scored$suburb,
              postcode = scored$postcode),

Two things in that table are worth more than any rule of thumb.

Surname looks useless, and is not. Its log-odds is near zero because every candidate pair already agrees on the surname code or the given-name code — blocking conditioned on it. A field cannot discriminate among pairs that were selected for agreeing on it. This is why the naive move of reading the weights straight off this table misfires, and why a real project fits the model on the pairs it will actually score, with the blocking in the model.

Postcode looks decisive, and is a trap. Its log-odds is the largest in the table, because two unrelated people rarely share a postcode. But the people who moved — one in ten here — disagree on it while being the same person. Weighting it by that log-odds buys precision on the easy pairs and loses exactly the matches that needed help. Address and suburb carry the same risk for the same reason, and the fix is to weight the identifiers that do not change (name, date of birth) far above the ones that do:

w <- c(surname = 3, given = 3, dob = 4, middle = 0.5, sex = 0.5,
       address = 0.75, suburb = 0.25, postcode = 0.5)

scored$score <- with(scored,
    (w["surname"]  * pmax(surname, surname_key) +
     w["given"]    * pmax(given, given_tokens) +
     w["dob"]      * dob +
     w["middle"]   * middle +
     w["sex"]      * sex +
     w["address"]  * address +
     w["suburb"]   * suburb +
     w["postcode"] * postcode) / sum(w))
round(quantile(scored$score, c(0, 0.5, 0.9, 0.99, 1)), 3)
   0%   50%   90%   99%  100% 
0.323 0.647 0.980 1.000 1.000

pmax(surname, surname_key) is the “either kind of agreement will do” idiom: the Jaro-Winkler score, or 1 if the two fingerprints are identical, whichever is kinder. The same for the two given-name comparators.

Hand weights are fine for a first pass as long as they are written down and swept (below). On real data, estimate them: fastLink and reclin2 fit Fellegi-Sunter weights, including the conditional-independence and blocking subtleties this section only gestures at.

The standardising in step 2 is a dozen passes over a column each. At 37,500 rows none of them is measurable, so here they are on a million — the size at which the choice starts to matter — against the base R equivalent:

ms <- function(f, reps = 3) {
    f()                                    # warm up
    start <- Sys.time()
    for (i in seq_len(reps)) f()
    round(1000 * (as.numeric(Sys.time()) - as.numeric(start)) / reps, 1)
}
bench <- function(label, fast, base = NULL) {
    f <- ms(fast)
    b <- if (is.null(base)) NA_real_ else ms(base)
    data.frame(step = label, fast_ms = f, base_ms = b,
               ratio = if (is.na(b)) NA_real_ else round(b / f, 1))
}

The wins are uneven, and that is the honest picture. The biggest ones are where base R is doing something structurally expensive: a strptime() and a strftime() per element for the dates, a strsplit() that allocates a list of pieces only to take one and throw the rest away, a gregexpr() that allocates a position vector per row only to take its length. Where base R is already doing one cheap pass in C, the gain is small — and sec-benchmarks lists the cases where base R is the faster choice outright.

The last two rows have no base R equivalent at all, which is the other half of the argument: the phonetic key and the similarity score are what make blocking and scoring possible in the first place, and the pipeline above is built out of them.
